# PMS 测试用例生成与优化

本技能以完整目录分发，包含SKILL.md、scripts、assets和requirements.txt。安装本技能后，在目标测试用例工作区调用即可开始；完整规则在本文定义，工具和输入示例随包提供；不依赖外部规范。

---

## 工具调用入口（v1.1）

技能目录为本SKILL.md的父目录；用户工作区与技能目录分别解析。始终调用包内脚本，不再每次临时编写Excel生成器。完整目录一起分享，接收方使用自己的环境和凭据。

```text
pms-test-case-authoring/
  SKILL.md
  requirements.txt
  scripts/case_tools.py
  assets/cases.example.json
```

1. 运行 `python "<技能目录>/scripts/case_tools.py" doctor` 检查依赖。缺openpyxl时可在用户选定虚拟环境运行 `python -m pip install -r "<技能目录>/requirements.txt"`；不擅自安装全局依赖。Python需3.10以上。
2. 初始化：`python "<技能目录>/scripts/case_tools.py" init --workspace "<测试用例工作区>"`。公用模板一致则复用，冲突时报错保留原件；已有检查清单保留团队定制。
3. Agent根据需求及PMS用例编写JSON，结构参照包内assets/cases.example.json。示例只演示格式，不作为真实验收或输出用例。metadata填写product、version、requirementCode、requirementName；cases使用31列中文字段，工具自动补默认值和需求编号。
4. 预置条件、执行步骤和预期结果使用非空字符串数组，步骤与预期逐项对应。每条mapping填写真实sourceRef和disposition（复用/修改/新增/待确认）；pmsCaseId、repoPath、featurePath、coverageRefs按实际来源填写，未知留空。仅有源路径不代表已核验业务。
5. 校验：`python "<技能目录>/scripts/case_tools.py" validate --input "<需求目录>/cases.json"`。错误返回非零退出码；修复输入后再生成。
6. 生成：`python "<技能目录>/scripts/case_tools.py" build --input "<需求目录>/cases.json" --output-dir "<需求目录>"`。输出31列Excel、case-mapping.csv和validation-report.json；缺依赖可显式追加 `--format csv`，不冒充Excel。
7. 复核实际工作簿表头、编号、需求编号、行数、样式及业务覆盖，交付说明区分结构校验和人工业务评审。输出已存在则更换版本目录，工具不覆盖历史。计划和执行字段保持为空，已有结果独立保留。

工具只执行本地文件操作，不访问PMS、不推送仓库、不执行环境测试。初始化无需openpyxl；仅XLSX生成需要该依赖。内置脚本属于技能资源，直接执行即可；另行编写或修改项目脚本仍遵守项目路径约定。

## 0. 首次使用与可移植配置

给接收方的启动指令：

> 请使用 $pms-test-case-authoring，在指定测试用例工作区初始化缺失的公用模板，根据 PMS 需求 <需求编号> 生成或优化用例。只生成本地文件，暂不写入 PMS、不执行环境测试。

将 pms-test-case-authoring 文件夹复制到接收方工具支持的 skills 目录即可分发；保留其中 SKILL.md 的名称和结构。接收方使用自己的 PMS 登录与工作区。

### 0.1 路径和输入解析

- WORKSPACE_ROOT：用户明确指定的测试用例工作目录；未指定时使用当前任务工作目录并在开始时说明。技能安装目录只保存技能规则，所有需求资料与生成产物写入 WORKSPACE_ROOT，不写进技能目录。
- COMMON_DIR：WORKSPACE_ROOT/公用；REQUIREMENT_DIR：WORKSPACE_ROOT/<需求编号或需求标题>。
- 产品、版本、需求编号、模块及维护人从用户输入或 PMS 实时查询解析；没有信息时只询问影响生成的必要项。不得继承分享者账号、电脑路径、旧部署地址或示例需求。
- 本文 AISS、2.3.0、ARS 等均为 AISS 场景示例。其他产品使用实际产品简称、版本和模块；31 列表头及列序保持不变。
- SCRIPT_ROOT：优先使用当前工作区已有的明确脚本存放约定；没有约定时，临时生成器位于 COMMON_DIR/tmp/<需求编号>，可复用生成器位于 COMMON_DIR/scripts。交付只含规则和数据时无需创建脚本目录。
- 此 AISS 安装脚本工作区仍遵守现有约定：脚本放安装脚本根目录下的 tmp 或 script；接收方不需要创建分享者的磁盘路径。

### 0.2 公用初始化协议

收到生成或初始化任务后，先检查现存文件，只创建缺失项：

1. 创建 COMMON_DIR；依据本文第 4 节展开全部 31 列表头，生成 UTF-8 BOM 的单行 `用例字段模板.csv`，第 27～31 列分别为截图1至截图5。
2. 创建 `通用测试检查清单.md`，内容包含：来源基线、已有用例复用、风险覆盖、步骤与预期对应、异步终态、文件正确性、语言隔离、角色权限、PMS 映射、证据与交付检查。具体判据使用本文第 8、9、11 节。
3. 为当前需求创建独立目录，以及需要的 source、evidence 子目录；先完成需求读取与去重，再生成工作簿和 case-mapping.csv。不得生成示例需求用例冒充真实用例。
4. 校验模板恰为 31 列、列序正确，无真实执行结果或凭据；在交付说明列出新建、复用和存在差异的文件。

已有公共文件先校验：一致则复用；不同则报告字段差异并生成带版本后缀的候选，不自动覆盖。需求文件和真实执行证据始终保留。重复初始化不得重复创建同一套产物。

公用目录由包内init工具重建，本文是规则来源。后续修改规范时带版本号更新；已有公共模板通过校验后才替换，不让新规范静默覆盖团队定制。

### 0.3 能力检测与降级

- 先探测 PMS CLI、Python 和 openpyxl 是否可用；使用当前工具提供的运行时或已安装解释器。缺依赖时报告缺项，不假设接收方已安装、不擅自全局安装。
- PMS 可用时通过 usage/schema 查询命令及字段，读取需求、已接受输入和现有用例。CLI 不可用或无权限时，可基于用户提供的需求资料生成本地草稿，标明来源及待核验项；PMS ID 不伪造。
- Python/openpyxl 不可用时，仍可生成标准 31 列 UTF-8 BOM CSV、映射和覆盖说明；明确 XLSX 样式未生成，不能把 CSV 改扩展名当作 XLSX。
- 仅准备本地用例时，不以缺少测试环境、PMS 写权限或未进入正式测试阶段作为阻塞。只有实际执行或登记时，才核对对应条件。

## 1. 目录结构约定

每个需求在本目录下创建独立子目录，可使用需求编号或需求标题；标题相同时加入需求编号区分，已有目录不因展示标题变化自动重命名：

```
测试用例/
├── 公用/                         ← 跨需求复用的模板、检查清单和已核实公共资料
│   ├── 用例字段模板.csv
│   └── 通用测试检查清单.md
├── <需求编号或需求标题>/          ← 每个需求独立目录
│   ├── <产品简称><版本>_<需求名称>_测试用例.xlsx
│   ├── case-mapping.csv
│   ├── <本需求方案及接口资料>
│   ├── source/
│   └── evidence/
└── <其他需求目录>/
```

**所有输出 xlsx 文件放在各自需求子目录下，不放在测试用例根目录。**

## 2. 从 PMS 获取需求文档

### 2.1 获取流程

```bash
# 1. 获取需求基本信息
pms requirement get REQ-2026-XXXXXX

# 2. 获取阶段上下文（含输入文档列表和 git blob 哈希）
pms stage context REQ-2026-XXXXXX

# 3. 先用 pms artifact usage 核对当前 CLI 的读取参数，再读取阶段输入
pms artifact read <artifactVersionRef>

# 4. 从本地 aiss-ai-coding-projects 仓库按 blob 哈希提取文档
REPO="<经PMS仓库信息及git remote核对后的本地仓库路径>"
git -C "$REPO" cat-file blob <blobHash> > <目标文件名>
```

### 2.2 文档优先级

- 以实时 `stage context` 的已接受输入、评审决定及明确覆盖关系确认实施依据，记录 commit、blob、artifactVersionRef 和查询时间。
- 方案文档（SOLUTION/DECOMPOSITION）为主要设计输入。
- `source/` 目录内的历史分析文档作为补充参考，不覆盖方案文档。

### 2.3 版本识别

artifact 的 `path` 字段中包含版本号（如 `reuse-design-v1.6.md`、`decomposition-v1.1.md`），
文件名版本号仅用于检索；较高版本可能是草稿，不能覆盖已接受基线。发现冲突时记录差异及待确认项。

## 3. 用例生成规则

### 3.1 核心原则

**核心业务以端到端场景为主，接口契约和局部校验允许独立成例。** 异步导出覆盖提交→任务→通知→下载→文件内容；options 字段契约、未登录拦截、弹窗字段校验可独立验证，并与对应业务场景建立映射。每条用例有明确目标和可判断的断言。

### 3.2 场景设计来源

按以下优先级推导测试场景：

1. PMS 需求分解文档（`decomposition-v*.md`）中的特性清单和验收映射
2. 方案文档（`reuse-design-v*.md`、`solution-summary.md`）中的接口契约和业务规则
3. 图片关联、国际化等专项设计文档
4. 2.0.0 版本场景模板（跨服务流）：
   - 设备上线：DCS（组织/用户）→ DMC（添加设备）→ DCS（目录绑定）→ AVS（视频平台同步）
   - 告警流：ARS（配置算法平台→创建场景→创建智能任务→启动任务）→ 设备触发事件 → ARS（告警事件记录）→ MGC（推送通知）
   - 录像：DMC（设备在线）→ AVS（录像计划）→ AVS（视频片段/抓拍查询）

### 3.3 用例分级定义

| 级别 | 范围 |
|------|------|
| **P0** | 冒烟——核心业务流端到端正向路径，不含删除/停止操作 |
| **P1** | UI 变更 + 基本功能（所有按钮级正向操作） |
| **P2** | 通用场景：批量操作、状态操作、功能交互、特性规格 |
| **P3** | 字段校验、系统/服务异常与边界场景 |
| **P4** | 文档、国际化、易用性、兼容性、周期性测试（系统级性能/可靠性/可服务性） |
| **P5** | 一次性动作（如数据迁移验证）——在移交时提供给开发自测 |

### 3.4 用例编号格式

```
AISS-{MODULE}-{LEVEL}-{SEQ}
```

- `MODULE`：服务缩写 —— `DMC` / `GW` / `MGC` / `ARS` / `DCS` / `AVS` / `POS`
- `LEVEL`：P0–P5
- `SEQ`：该 module+level 下 3 位零填充序号，如 `001`

示例：`AISS-ARS-P1-003`

## 5. 生成脚本约定

### 5.1 技术栈

- Python + openpyxl
- 生成器使用第 0 节解析后的 SCRIPT_ROOT；以显式输出目录参数定位需求目录。需求目录存放用例、映射和来源文档。
- 输出文件：`{产品简称}{版本}_{需求名称}_测试用例.xlsx`；名称按接收方系统的文件名规则清理非法字符。

### 5.2 输入与生成约定

使用包内case_tools.py，按工具调用入口生成JSON并执行validate/build；路径通过参数传入。不得将特定需求数据硬编码进公共工具。输出文件名由metadata生成，非法文件名字符自动清理。

工具不修改现有工作簿，不导入或迁移既有执行结果；如需更新，保留原件并在新的版本目录输出。结构化校验不判断业务预期正确性、PMS身份真实性或覆盖完整性，Agent仍负责这些评审。

## 6. 工作流程

1. **获取需求**：`pms requirement get` + `pms stage context` + `pms artifact read` → 提取 blob → 保存到需求子目录
2. **阅读文档**：按已接受输入与明确覆盖关系读取方案、分解和接口合同；文件名只作为检索线索
3. **设计场景**：以需求分解中的特性清单（F001–F00X）和验收映射为主骨架，补充边界/异常/国际化场景
4. **编写数据**：按包内示例输出cases.json，调用case_tools.py validate与build；不重复编写生成器
5. **生成并验证**：逐行检查 31 列、编号唯一、必填项、步骤与预期对应；再检查行数、表头、换行、筛选、冻结与代表性长文本。

## 7. 不在此处维护的内容

- 具体的接口实现代码（在 `aiss-ai-coding-projects` 仓库）
- PMS 阶段推进、评审决定（由责任人在 PMS 操作）
- 测试执行记录、截图（保存在需求执行证据目录并填写 xlsx/PMS 对应引用，不写入本规范）
- 已完成需求的历史 blob 哈希（保留在需求子目录的文档文件中）

## 8. PMS 用例复用与身份核验

创建用例前先读取本节；本地生成、PMS 登记和测试执行是三个独立动作。

1. 查询需求基本信息和阶段上下文，确认 productId、requirementId、版本、仓库及已接受输入。
2. 查询 `pms test-case list` 与 `scenario-list`。先按需求编号检索，再按标题、业务关键词和 featurePath 补查；按 hasMore 翻页。编号检索无结果不能证明没有用例。
3. 对命中用例读取 `pms test-case steps <caseId> --product <productId>`，比较目标、数据、步骤、断言及覆盖范围；逐条标记复用、修改、补充或待确认。
4. 本地生成不需要 PMS 写入。登记或更新前核对当前凭据身份、产品权限、writesEnabled 和目标对象；需求负责人或 stage context 的 actor 不能单独证明浏览器账号身份。身份不一致时先澄清，不代替用户切换凭据。
5. CLI 命令与字段以安装版本的 usage/schema 为准。PMS 写入需用户授权；本地生成请求本身不代表授权提交 PMS、推进阶段或结算轮次。

保持既有 31 列格式，额外维护 `case-mapping.csv`：

`requirementCode,localCaseNo,pmsCaseId,repoPath,featurePath,sourceRef,coverageRefs,disposition`

- localCaseNo 在同一工作簿唯一；跨需求以 requirementCode + localCaseNo 联合识别，避免通用编号碰撞。
- PMS ID、repoPath、featurePath 读取真实对象；无对应项时留空并标记待登记。
- 第 15 列从当前 PMS 需求的 requirementCode 自动填充，并与映射记录的 requirementCode 保持一致；区分产品编号、需求编号和内部 requirementId，使用对应需求的可读编号。现网问题填写实际问题单号。无法确认编号时留空，在交付说明中列为待确认，不在该列添加解释。
- sourceRef 指向来源文件及 commit/artifact；coverageRefs 记录验收编号，可一对多。
- API/UI 可验证同一业务的不同层次，但各自写清观察点；目标、数据和断言相同的用例合并或标记重复候选。
- 特性绑定核对业务语义和真实特性树，既有绑定也需复核，不能机械复制。

## 9. 可执行用例与证据标准

每条用例必须具备：测试目标、用户角色、环境/版本、前置数据及数量、操作步骤、逐步预期、业务通过标准和适用的清理要求。未知接口字段、阈值、超时时间标记待确认并指向来源，不编造数值。

- 前置条件描述执行前已成立的事实；步骤只写动作；预期结果逐步对应并写可观察断言。通常以三段组织业务流，步骤数按场景调整。
- 正向、负向、边界、安全按需求风险覆盖；不为凑分类数量制造重复用例。
- P0～P5 是本地分类，不直接等同 PMS 的 objective 或 verificationType。高风险权限、数据丢失、消息恢复仍按风险确定发必测范围，不因属于异常场景而降级。
- 自动化可行性与自动化已完成分开填写；已自动化须有脚本路径和实际运行证据。
- 新生成用例的执行日期、执行结果和截图为空；保留已有真实执行记录，新增验证使用独立轮次/运行。
- 异步接口返回任务 ID 只证明受理。通过需验证终态、当前用户通知、下载可用和最终产物；失败路径确认明确错误及无错误成功文件。
- 文件验证检查实际格式、可读性、列顺序、记录集合与数量、业务字段、图片可解码及关联关系；记录文件哈希和证据位置。
- 国际化验证请求语言、通知、页面、文件的完整链路及并发语言隔离；稳定 ID 不随展示语言改变。
- 权限验证覆盖普通用户、未登录、未授权记录和跨用户下载；管理员单账号通过不能代替权限覆盖。
- 区分数据缺失、菜单不可达、环境故障、脚本故障和产品缺陷；阻塞写明原因及恢复条件。实际执行结果才能填通过。
- PMS lastResult 未限定版本/轮次时只作线索；正式结论绑定版本、轮次、环境、run、caseId、executionRef 和证据。Agent 辅助验证按实际来源记录，不冒充人工正式结果。

## 10. 公共资料与需求资料归属

- `公用/` 存放跨需求可直接复用的字段模板、通用测试检查清单及经过独立核实的公共资料；不得包含某一需求专属的验收、接口、用例、结果或历史记录。
- 各需求目录仅保存该需求的来源快照、方案、接口合同、用例、PMS 映射、评审和执行证据。告警导出只是一个需求示例，不作为其他需求的固定目录或业务模板。
- 文件名含“项目”“环境”“通用”不代表内容可公用；若内容包含需求专属分支、提交、接口边界或评审状态，保留在原需求目录。
- 混合资料先提取可独立成立的通用内容到公用目录，需求快照保留原样；不得把单次环境观测推广为跨需求现状。
- 公共资料不存账号凭据。脚本按第 0 节解析后的目录存放；明确的工作区约定优先。
- 迁移文件时先检查调用和链接，核对目标路径及内容一致性，再更新受影响引用。需求专属原始输入保持可追溯。
- 本规范完整保留执行所需的格式与规则，Agent 可独立使用本文件；公用目录提供可复用产物，不构成额外规范读取前置条件。

## 11. 交付检查

完成前核对：31 列格式保持；编号无重复；来源和验收映射可追溯；已有 PMS 用例已比对；复用与新增有说明；每步预期可验证；新用例无虚构执行结果；专项矩阵缺口列明；输出路径正确；未变更需求原文、账号凭据或 PMS 状态。

交付说明列出生成/修改数量、输出文件、验证方式、未覆盖项及待确认合同。生成用例完成不代表执行完成或发布验收通过。

## 12. 脚本变更边界

本规范维护不涉及部署脚本执行。实际修改脚本时，检查调用方、下游依赖、单机/集群兼容、失败/超时/重试/清理、幂等及重入；同轮在工作区根级脚本修改记录中登记改动、收益、验证命令、未验证范围和残余风险。发现脚本或流程优化点时，同轮记录问题、影响及建议。
